# Invoice Keeper — напоминания о регулярных платежах

Веб-панель + Telegram-напоминания о регулярных платежах: администратор заводит
платежи, система напоминает в чат за 3 дня до срока, пользователи отмечают оплату
и видят просрочки.

## Стек

| Слой           | Технологии                                                          |
| -------------- | ------------------------------------------------------------------- |
| Backend        | Python 3.12, FastAPI, Uvicorn, SQLAlchemy 2.0, Alembic, Pydantic v2 |
| База           | SQLite (файл `backend/instance/app.db`)                             |
| Frontend       | JavaScript (без фреймворка), Vite, Tailwind CSS, Axios              |
| Инфраструктура | Docker, docker-compose                                              |

## Что уже работает (этап «каркас»)

- Авторизация по JWT, две роли: администратор и пользователь.
- Роли проверяются **на сервере**: обычный пользователь не выполнит действие
  администратора даже через API.
- Все обязательные эндпоинты кейса, Swagger (`/api/v1/docs`) и OpenAPI-спецификация.
- Схема БД (4 таблицы) и одна миграция Alembic.
- Единый формат ошибок, тесты на роли, доступ и контракт.

Реализовано в `app/services/` и `app/worker.py`:

| Модуль                  | Что делает                                                                         |
| ----------------------- | ---------------------------------------------------------------------------------- |
| `services/periods.py`   | генерирует периоды платежа: своя дата и своя отметка «Оплачено / Не оплачено»      |
| `services/reminders.py` | выбирает неоплаченные периоды в окне 3 дней и отправляет напоминания без дублей    |
| `services/telegram.py`  | отправляет сообщения в Telegram Bot API                                            |
| `worker.py`             | фоновый процесс: проверяет сроки по расписанию (`REMINDER_CHECK_INTERVAL_SECONDS`) |

Сценарии приёмки на эту логику — в `backend/tests/test_domain_logic.py`; они помечены
`skip` и разблокируются снятием пометки, когда логика будет проверена вручную.

### Схема данных

Четыре таблицы: `users`, `recurring_payments` (шаблоны), `payment_occurrences`
(периоды), `revoked_tokens` (завершённые сессии).

Роль в базе **не хранится**: администратор — это аккаунт, чей логин совпадает с
`ADMIN_USERNAME` из `.env`. Значит база не может разойтись с настройкой, а роль
в API (`role: "admin" | "user"`) считается на лету.

Период — **слепок** шаблона: при создании он копирует `name`, `amount`, `currency`
и хранит `payment_ended_at` (когда платёж прекратили). Поэтому любой список
периодов читается по одной таблице, без JOIN, и все фильтры (`state`, `status`,
`currency`, `recurring_payment_id`, даты) работают по ней же. Шаблон нельзя
изменить через API — есть только создать и прекратить, — так что слепок не
расходится с оригиналом.

Просрочка и статус периода **не хранятся**, а считаются при чтении: так
исправление фактической даты оплаты сразу убирает ошибочную просрочку, а срок
не меняется.

### Что убрали и почему

Каркас — это минимум, который нужен для работы приложения. Необязательное убрано:

| Убрали                                            | Почему                                                                             |
| ------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Журнал действий (`audit_logs`)                    | Бонусная фича из кейса, а не обязательное условие приёмки                          |
| Отдельный процесс `worker`                        | Пока напоминания не реализованы, процессу нечего делать; добавляется вместе с ними |
| Файловые логи с ротацией                          | Хватает stdout (`docker compose logs`)                                             |
| Разбор ошибок pydantic по полям                   | Осталось первое сообщение об ошибке — фронту этого достаточно                      |
| `GET /recurring-payments/{id}`, `GET /users/{id}` | Их нет в списке эндпоинтов кейса                                                   |

## Быстрый старт (Docker)

Нужны Docker и Docker Compose. База отдельно не нужна, это SQLite.

```bash
# 1. Настройки: копируем шаблон
cp .env.example .env

# 2. В .env обязательно:
#    JWT_SECRET_KEY — случайная строка (openssl rand -hex 32)
#    SUPERADMIN_*   — логин, пароль и email администратора
#    TELEGRAM_*     — для напоминаний (см. «Настройка Telegram»)

# 3. Запуск
docker compose up --build
```

> Пишите `--build` после каждого `git pull`. Иначе Docker возьмёт старый образ.

Поднимаются три сервиса:

| Сервис | Что делает | Адрес |
|--------|-----------|-------|
| `backend` | API (FastAPI). При старте применяет миграции, сверяет схему БД и создаёт администратора и демо-данные | http://localhost:5000 |
| `frontend` | Веб-панель (Vite) | http://localhost:5173 |
| `worker` | Фоновые напоминания по расписанию и Telegram-бот (кнопка «Оплачено», привязка аккаунтов) | — |

Полезные адреса:

| Что | Адрес |
|-----|-------|
| Панель | http://localhost:5173 |
| Swagger | http://localhost:5000/api/v1/docs |
| OpenAPI (живая) | http://localhost:5000/api/v1/openapi.json |
| OpenAPI (файл) | [`backend/openapi.json`](backend/openapi.json) |
| Проверка живости | http://localhost:5000/api/v1/health |

Остановка: `docker compose down`. Данные при этом сохраняются (см. [Хранение данных](#хранение-данных-миграции-сброс-базы)).

Без настроенного Telegram приложение работает полностью. Напоминания просто не
отправляются, и worker пишет об этом в лог.

## Сценарий демонстрации

Полный путь из кейса: от добавления платежа до следующего периода.

**Основной сценарий**

1. **Войти администратором.** Откройте http://localhost:5173 и войдите как `manager@example.com` / `manager12345` или как суперадмин из `.env`.
2. **Добавить регулярный платёж.** Вкладка «Регулярные» → «+ Добавить платеж». Укажите название, сумму, валюту, периодичность и дату ближайшей оплаты. Возьмите дату не дальше чем через 3 дня, чтобы напоминание пришло сразу.
3. **Получить напоминание в Telegram.** Сообщение придёт в чат из `TELEGRAM_CHAT_ID` сразу после создания платежа. В нём будут название, сумма, валюта, дата и кнопка «✅ Оплачено».
4. **Войти пользователем и отметить оплату.** Выйдите и войдите как `user@example.com` / `user12345`. На вкладке «Платежи» нажмите «Оплатить» у нужного периода. Отметить оплату можно и кнопкой «Оплачено» в Telegram, если аккаунт привязан (см. [Настройка Telegram](#настройка-telegram)).

**Просрочка и периоды**

5. **Показать просроченный платёж.** Создайте платёж с датой в прошлом, например неделю назад. Он сразу появится со статусом «Просрочка N дн.», а сумма попадёт в «из них просрочено» на карточке валюты. Фильтр «Просрочено» покажет только такие платежи.
6. **Исправить фактическую дату оплаты.** Отметьте просроченный период оплаченным: статус станет «оплачено · опоздание N дн.». В колонке «Действие» поменяйте дату в календаре на день срока. Опоздание исчезнет, а срок останется прежним.
7. **Показать следующий период с отдельным статусом.** Как только текущий период оплачен, в списке появляется следующий (через месяц, квартал или год) со своим статусом «Не оплачено». Прошлый период остаётся в истории.

## Роли и права

В кейсе две роли: администратор и пользователь. В решении администратор из
`.env` — это **суперадмин** (в интерфейсе подписан как *owner*). Он может всё,
что требуется от администратора по кейсу. Дополнительно он может назначать
обычных администраторов, чтобы не раздавать всем один пароль из `.env`.

| Действие | Суперадмин (owner) | Администратор | Пользователь |
|----------|:---:|:---:|:---:|
| Смотреть платежи, периоды и итоги | ✅ | ✅ | ✅ |
| Отмечать и отменять оплату, исправлять фактическую дату | ✅ | ✅ | ✅ |
| Добавлять и прекращать регулярные платежи | ✅ | ✅ | ❌ |
| Создавать, менять и удалять обычных пользователей | ✅ | ✅ | ❌ |
| Журнал оплат (`GET /payments`) | ✅ | ✅ | ❌ |
| Создавать и менять администраторов, менять роли | ✅ | ❌ | ❌ |

- Суперадмин задаётся **только в `.env`** (`SUPERADMIN_USERNAME`, `SUPERADMIN_PASSWORD`, `SUPERADMIN_EMAIL`). Через панель и API его нельзя изменить, удалить или создать второго. При каждом старте контейнера сид `scripts.seed_superadmin` приводит аккаунт к значениям из `.env`.
- Логин и email суперадмина зарезервированы: занять их другим пользователем нельзя.
- Ограничения действуют в API, а не только в интерфейсе. Скрытые кнопки в панели — лишь удобство.
- После удаления пользователя его токен перестаёт работать. В истории оплат вместо него остаётся пустая ссылка.

## Правила учёта: периоды, статусы, просрочка

**Регулярный платёж** — это шаблон: название, сумма, валюта, дата ближайшей
оплаты и периодичность (ежемесячно; дополнительно ежеквартально и ежегодно).

**Период** — конкретная оплата шаблона со своей датой и отметкой «Оплачено / Не оплачено».

- Периоды создаются от первой даты с шагом периодичности, вплоть до ближайшего неоплаченного периода со сроком сегодня или позже. Если первая дата в прошлом, создаётся вся история.
- Оплатили текущий период — сразу появляется следующий.
- Просрочка не останавливает следующие периоды: когда наступает новый срок, появляется новый период.
- Если такого числа в месяце нет, срок переносится на последний день месяца. Даты считаются от исходного числа, без «уползания»: 31.01 → 28.02 → 31.03.
- Все даты («сегодня», просрочка, окно напоминаний) считаются в едином часовом поясе `APP_TIMEZONE`, а не в поясе сервера.

**Статусы периода**

| Состояние | Когда |
|-----------|-------|
| Ждёт оплаты (`pending`) | Не оплачено, срок сегодня или позже |
| Просрочено (`overdue`) | Не оплачено, со **следующего дня** после срока |
| Оплачено (`paid`) | Оплачено в день срока или раньше. Оплата в день срока — вовремя |
| Оплачено с опозданием (`paid_late`) | Оплачено после срока |

- При отметке «Оплачено» указывается фактическая дата. Без даты ставится сегодня. Будущую дату указать нельзя.
- При отмене отметки дата оплаты очищается.
- Просрочка не хранится в базе, а считается при чтении. Поэтому исправление фактической даты сразу убирает ошибочную просрочку, а срок не меняется.

**Прекращение платежа** (`DELETE /recurring-payments/{id}`): платёж становится
неактивным, новые периоды и напоминания больше не создаются. Будущие
неоплаченные периоды удаляются. Оплаченные и уже наступившие периоды остаются
в истории с пометкой «платёж прекращён».

## Напоминания

Как это работает:

1. Worker раз в `REMINDER_CHECK_INTERVAL_SECONDS` (по умолчанию 60 с) досоздаёт недостающие периоды и проверяет сроки.
2. Он выбирает **неоплаченные** периоды **действующих** платежей со сроком в окне *от сегодня до сегодня + `REMINDER_DAYS_BEFORE`* (по умолчанию 3 дня), по которым ещё не напоминали.
3. Отправляет сообщение: название, сумма, валюта, дата оплаты и сколько осталось дней.

Правила:

- **Без дублей.** Перед отправкой период «захватывается» атомарным `UPDATE … WHERE reminder_sent_at IS NULL`. Повторная проверка или параллельный процесс второй раз его не отправят.
- **Платёж добавлен позже чем за 3 дня до срока** — напоминание уходит сразу при создании, не дожидаясь worker.
- **Оплаченный период** напоминания не вызывает.
- **Прекращённый платёж** напоминаний не создаёт.
- **Сбой отправки.** Если все каналы упали, отметка снимается, и на следующей проверке будет новая попытка.

Каналы:

| Канал | Куда | Условие |
|-------|------|---------|
| Telegram | Чат `TELEGRAM_CHAT_ID`, с кнопкой «✅ Оплачено» | Заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` |
| Email (SMTP) | Всем пользователям с email, одним письмом со скрытыми получателями. Адреса `@example.com` (демо) пропускаются | Заданы `SMTP_ADDR` и `SMTP_PASSWORD` |

## Настройка Telegram

1. Создайте бота через [@BotFather](https://t.me/BotFather) и получите токен.
2. Добавьте бота в групповой чат, куда должны приходить напоминания.
3. Узнайте `chat_id` чата. Напишите в группе `@имя_бота тест`: из-за privacy mode бот видит только сообщения, где его упомянули. Затем откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и возьмите поле `chat.id`. У группы он отрицательный.
4. Пропишите в `.env`:

   ```env
   TELEGRAM_BOT_TOKEN=123456:ABC-DEF...
   TELEGRAM_CHAT_ID=-1001234567890
   TELEGRAM_BOT_USERNAME=имя_бота
   ```

5. Перезапустите: `docker compose up -d --build`.

Если Telegram настроен, `GET /api/v1/health` вернёт `"telegram_configured": true`.

**Кнопка «Оплачено» в сообщении.** Чтобы бот понимал, кто нажал кнопку,
Telegram-аккаунт нужно привязать к пользователю системы. Есть три способа:

| Способ | Как |
|--------|-----|
| Ссылка на бота | `POST /api/v1/auth/telegram-link` возвращает одноразовую ссылку `t.me/<бот>?start=<код>`. Откройте её и нажмите «Start». Код живёт 15 минут и работает один раз |
| Ссылка-приглашение в чат | `POST /api/v1/auth/telegram-chat-link` возвращает персональную ссылку-приглашение. Бот привяжет аккаунт, когда человек вступит в чат. Нужен `TELEGRAM_GROUP_CHAT_ID`, а бот должен быть администратором чата с правом приглашать участников |
| Вручную | Напишите боту любое сообщение, он ответит вашим Telegram ID. Передайте его в `PATCH /api/v1/auth/me` (`{"telegram_id": 123}`) |

В журнале оплат будет имя пользователя из системы и источник `telegram`.
Кнопку и привязку обслуживает сервис `worker`, поэтому он должен быть запущен.

```bash
# Вход
curl -X POST http://localhost:5000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "manager@example.com", "password": "manager12345"}'

# Создать платёж
curl -X POST http://localhost:5000/api/v1/recurring-payments \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name": "Аренда офиса", "amount": "85000", "currency": "RUB",
       "first_due_date": "2026-10-25", "period": "monthly"}'

# Просроченные периоды
curl "http://localhost:5000/api/v1/payment-occurrences?state=overdue" \
  -H "Authorization: Bearer $TOKEN"
```

Варианты тела `PATCH /payment-occurrences/{id}`:

| Тело | Что делает |
|------|-----------|
| `{"status": "paid"}` | Оплачено сегодня |
| `{"status": "paid", "paid_at": "2026-10-20"}` | Оплачено в указанную дату |
| `{"paid_at": "2026-10-19"}` | Исправить дату у оплаченного периода (просрочка пересчитается) |
| `{"status": "unpaid"}` | Отменить отметку, дата очищается |

Фильтры `GET /payment-occurrences`: `state` (`pending`, `overdue`, `paid`,
`paid_late`, `unpaid_all`), `status`, `currency`, `recurring_payment_id`,
`date_from`, `date_to`, `include_inactive`, `include_future`, `order`.

`GET /payments/summary` принимает `date_from`, `date_to` (по сроку оплаты) и
`on_date` — дату, на которую считаются статусы. По каждой валюте возвращаются
суммы и количества: всего, оплачено, не оплачено, просрочено.

**Формат ошибок** единый для всех ответов:

```json
{"code": 403, "status": "Forbidden", "message": "Действие доступно только администратору"}
```

## Миграции

Схема БД хранится в `backend/migrations/` и коммитится в git — у всех в команде
одинаковая структура таблиц.

```bash
# применить миграции
alembic upgrade head

# изменили модель — создать миграцию
alembic revision --autogenerate -m "что изменили"
alembic upgrade head
```

В Docker добавьте `docker compose exec backend`, например:

```bash
docker compose exec backend alembic upgrade head
# изменили модель:
docker compose exec backend alembic revision --autogenerate -m "что изменили"
```

При старте `scripts.check_schema` сверяет схему базы с моделями. Если схема
разошлась, контейнер не поднимется и напишет в логе, чего не хватает.
Пересоздать базу (данные удалятся, суперадмин и демо-данные создадутся заново):

```bash
docker compose exec backend python -m scripts.reset_db -y
docker compose up -d backend
```

Если данные нужно сохранить (например, в on-premise с реальными платежами) —
пишите настоящие миграции: `alembic revision --autogenerate -m "что изменили"`
и `alembic upgrade head`.

Папка `backend/scripts/` — скрипты, которые наполняют базу. Каждый лежит в
отдельном файле с функцией `run(db)`, `seed_all.py` запускает их по списку.
Скрипты идемпотентные: повторный запуск не создаёт дубликаты.

```bash

```

- `seed_admin` — администратор из `.env` (логин и пароль обновляются при смене `.env`).
- `seed_demo` — демо-данные: аренда в рублях, сервер в долларах, подписка в евро
  и два пользователя (`user` / `user12345`, `anna` / `anna12345`). Отключается

Служебные скрипты (запускаются отдельно, не сиды):

| Скрипт                             | Что делает                                                              |
| ---------------------------------- | ----------------------------------------------------------------------- |
| `python -m scripts.check_schema`   | сверяет схему базы с моделями, при расхождении — ненулевой код возврата |
| `python -m scripts.reset_db`       | пересоздаёт базу по актуальным моделям (данные пропадают)               |
| `python -m scripts.export_openapi` | обновляет `backend/openapi.json`                                        |

### Диагностика: почему не работает

Эти скрипты проверяют настройки **тем же кодом, что и приложение**, и
называют конкретную причину сбоя вместо «ошибка соединения»:

```bash
# внутри контейнера
docker compose exec backend python -m scripts.check_telegram
docker compose exec backend python -m scripts.check_smtp

# или на сервере, из папки backend/
python -m scripts.check_telegram --send
python -m scripts.check_smtp --to me@example.com
```

Код возврата: 0 — всё в порядке, 1 — есть проблема.

`check_telegram` проверяет токен, чат, прокси и доступность бота; с `--send`
отправляет тестовое сообщение. `check_smtp` — настройки SMTP, подключение,
вход и (с `--to`) тестовое письмо.

Оба пишут в stdout отчёт и в лог — структурированные события
(`telegram.call_failed`, `smtp.connection`, …), чтобы по логам было видно
историю проверок.

Запускайте именно так, из папки `backend/`: при прямом запуске файла
(`python scripts/seed_all.py`) импорты не сработают.

## Telegram-напоминания

1. Создайте бота через @BotFather и получите токен.
2. Узнайте `chat_id` чата: напишите боту любое сообщение и откройте
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` — нужное поле `chat.id`.
   Для группы id отрицательный, и в группе надо написать `@твой_бот тест`
   (privacy mode: бот видит только сообщения, где его упомянули).
3. Пропишите в `.env`:

```
TELEGRAM_BOT_TOKEN=123456:ABC-DEF...
TELEGRAM_CHAT_ID=-1001234567890
```

4. Напоминания рассылает отдельный процесс — `backend/app/worker.py`:

```bash
cd backend
python -m app.worker
```

В Docker он поднимается отдельным сервисом `worker` (см. `docker-compose.yaml`).
Worker не запускает миграции — этим занимается `backend`, иначе два процесса
одновременно меняли бы одну SQLite-базу.

Напоминание приходит минимум за `REMINDER_DAYS_BEFORE` дней (по умолчанию 3) до
срока: название, сумма, валюта и дата оплаты. Дублей нет: период помечается
отправленным атомарным UPDATE, повторная проверка его не отправляет заново.
Оплаченный период напоминания не вызывает.

## Частые проблемы

**`alembic upgrade head` не находит ревизию**

В базе осталась старая версия миграций. Начните с чистой базы: остановите
контейнеры, удалите `backend/instance/app.db` и повторите миграцию.

**`/api/v1/docs` не открывается**

Бекенд не запущен или упал при старте. Смотрите `docker compose logs backend`.
Частая причина — не прошла миграция: сообщение будет в логах при старте.

**Страница показывает «Не удалось получить данные с сервера»**

Бек не запущен или адрес в `VITE_API_URL` неверный. Смотрите вкладку Network
в DevTools браузера.

**401 вместо сообщения об ошибке**

Токен истёк или был завершён через `POST /api/v1/auth/logout`. Войдите заново.

**После смены зависимостей фронта в Docker остались старые пакеты**

`node_modules` лежит в анонимном томе. Пересоберите:

```bash
docker compose up --build --renew-anon-volumes
```

**Ошибка «address already in use»**

Порт 5000 занят. Поменяйте его в `docker-compose.yaml` (и в `VITE_API_URL`).

## Логирование

Пишутся в stdout — их видно в `docker compose logs backend`.

### Настройки

В `.env`:

| Переменная            | Значение  | Смысл                                                                                     |
| --------------------- | --------- | ----------------------------------------------------------------------------------------- |
| `LOG_LEVEL`           | `INFO`    | Уровень корневого логгера. `DEBUG` показывает SQL-запросы — шумно, но полезно при разборе |
| `LOG_FORMAT`          | `text`    | `text` — читаемо; `json` — одна строка JSON на запись (удобно для сервера и парсинга)     |
| `LOG_LEVEL_LIBRARIES` | `WARNING` | Уровень для uvicorn/httpx/sqlalchemy. `WARNING` — только проблемы, без рутины             |

### Обычные записи

```python
from app.logging_config import get_logger

logger = get_logger(__name__)

logger.info("Пользователь зарегистрирован")   # обычное событие
logger.warning("Email уже занят")             # предупреждение
logger.exception("Ошибка при сохранении")     # с трейсбеком
```

### Структурированные события

Для разбора «что и когда произошло» — `log_event`: событие получает имя, детали
становятся отдельными полями. В JSON-формате это отдельные ключи, в текстовом —
`key=value` в конце строки.

```python
from app.logging_config import log_event

log_event(logger, logging.INFO, "reminder.sent",
          occurrence_id=42, name="VPS-сервер", due="2026-11-01")
```

```
00:12:03 | INFO | app.reminders | reminder.sent | occurrence_id=42 name=VPS-сервер due=2026-11-01
```

Поля со значением `None` отбрасываются: «не применимо» и «не задано» — разные
вещи, и в логах это видно.

### Замер времени

```python
from app.logging_config import timed

with timed(logger, "worker.check_pass"):
    check_and_send(db)
```

В лог попадает `duration_ms`. Исключение `timed` не подавляет — только
добавляет в запись `error` и переводит её в ERROR.

### Контекст запроса

Middleware (`app/middleware.py`) даёт каждому HTTP-запросу короткий `request_id`
и кладёт его в контекст. Внутри обработчика любая запись лога содержит этот id
и пользователя — цепочку записей одного запроса можно найти по id:

```
00:42:55 | INFO | app.request | http.request | request_id=4fc6ffa40d0a user=cheremsha#9 method=GET path=/api/v1/auth/me status=200 duration_ms=8.8
```

`request_id` также возвращается в заголовке `X-Request-ID` — по нему можно
связать запись сервера с записью клиента.

Журнал обращений: одна запись на запрос (метод, путь, статус, длительность).
4xx — WARNING, 5xx — ERROR. Служебные пути (`/api/v1/health`, `/api/hello`)
в журнал не пишутся.

### Диагностические скрипты

Проверяют настройки тем же кодом, что и приложение, и называют конкретную
причину сбоя:

```bash
docker compose exec backend python -m scripts.check_telegram
docker compose exec backend python -m scripts.check_smtp
```

Код возврата: 0 — всё в порядке, 1 — есть проблема.

`check_telegram` проверяет токен, чат, прокси и (с `--send`) отправляет
тестовое сообщение. `check_smtp` — настройки SMTP, подключение, вход и
(с `--to <адрес>`) тестовое письмо.

### Логи в тестах

`caplog` работает: `setup_logging` удаляет только свои обработчики и не трогает
перехватчик pytest.

```python
def test_reminder_sent(caplog):
    caplog.set_level(logging.INFO)
    ...
    record = next(r for r in caplog.records if getattr(r, "event", None) == "reminder.sent")
    assert record.occurrence_id == 42
```

Тесты самого логирования — `backend/tests/test_logging.py`,
журнала обращений — `backend/tests/test_request_logging.py`.
